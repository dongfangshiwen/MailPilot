# 1.3.0 普通聊天与上下文整理

## 旧版有什么

1.2.x 对长邮件／附件有分段摘要，但对聊天历史只取最后 6 条，再按有限字符预算截取。更早消息没有滚动摘要，长期对话中的目标、偏好及约定可能不再进入请求。这与持久保存聊天记录是两件事。

## 开源方案比较

查阅日期：2026-09-07。以下是官方项目与文档中的机制比较，并非本项目对这些系统进行过性能评测。

| 方案 | 机制 | 对 MailPilot 的适用性 |
| --- | --- | --- |
| [LangMem](https://github.com/langchain-ai/langmem) / [SummarizationNode](https://langchain-ai.github.io/langmem/reference/short_term/) | 超预算时生成摘要；保存滚动摘要和已整理消息 ID；保留工具调用与结果的完整关系 | 适合借鉴“摘要 + 近期消息 + 持久检查点”的方法 |
| [OpenHands Condenser](https://docs.openhands.dev/sdk/arch/condenser) / [源码](https://github.com/OpenHands/software-agent-sdk) | 按阈值触发，保留开头和近期事件，压缩中段；保留原事件日志和压缩记录 | 适合借鉴保留原始历史、保留目标和近期对话、逐步更新摘要 |
| [Microsoft LLMLingua / LLMLingua-2](https://github.com/microsoft/LLMLingua) | 专门的压缩模型在 Token 层面删减提示内容；提供 XLM-RoBERTa、BERT 等压缩模型示例 | 需要额外模型运行环境或服务，不符合本版不内置模型权重的约束，未引入 |

本版独立实现前两类方案的通用思路，没有将 Python 框架、专用压缩模型或远程记忆服务嵌入 APK，也不声称达到其他项目公布的压缩率。

## 当前实现

1. 先为系统提示、工具定义、本次问题及最大输出长度留出预算。有已选邮件时，再分配资料与聊天历史的空间；没有资料时，历史使用可用空间。
2. 历史在预算内时完整提交，不因“超过 6 条”而丢弃前文。
3. 超预算时，尽量保留最近两轮完整问答，并保留长度允许的最初用户问题。早期消息、超长单轮消息分批整理为滚动摘要。摘要要求保留目标、偏好、事实、数字、日期、来源编号、修正和待办，区分用户要求与助手推测。
4. 已有摘要通过最后已整理消息 ID 复用，下一次只处理新增的早期消息。改用较小上下文模型时，过大的旧摘要也会分批重新整理。单次最多 24 批，超限明示提示。
5. 所有批次成功且摘要满足长度约束后，才更新 Room 中的摘要、消息边界和条数。原始聊天记录始终保留。整理过程中取消、断网、得到空摘要／过长摘要或会话范围变化时，不覆盖旧摘要。整理成功后再停止正式回答，已完成的摘要仍可复用。
6. 摘要作为历史参考消息进入请求，不作为系统规则或新授权。压缩请求不提供工具。自 1.6 起，同一账号内更改资料选择保留当前会话和历史分析，每轮保存独立资料快照；当前请求不重新读取已经取消选择的附件原文。不同账号及不同会话继续隔离。

预算采用每字符约 2 Token 的保守估算，并为 JSON 包装预留空间，不是服务商的精确 Token 计数。工具调用进行中的协议消息保留完整；若其累积超过配置容量，会提示调整任务或模型容量，不截断工具参数。PDF 和图片继续通过原视觉流程处理。

上下文整理使用当前配置的模型及思考参数，会产生额外模型请求与 Token 用量。它是有损摘要，质量取决于模型，不保证记住所有细节。摘要不满足长度要求时明确失败，用户可重试、调整上下文或新建对话，完整原文仍可查看。

## 界面与独立聊天

- 设置中添加模型后即可聊天，无需添加邮箱；没有模型时，首页优先引导添加模型。
- 邮箱作为可选资料来源，收发、检索和邮件草稿才需要连接邮箱。没有邮箱时不向模型提供邮箱工具，即使模型自行返回工具调用，也会拒绝执行。
- 整理时显示批次进度；完成后显示“已整理 N 条早期消息”，点击可查看当前会话摘要。原文仍在聊天记录中，可以继续补充、纠正模型。
- 普通聊天以独立会话保存；添加或切换邮箱后仍能从历史列表打开。新对话不继承其他会话摘要。
- Room 2 → 3 自动迁移增加三列；旧版 1 → 2 → 3 升级链保留。清理聊天记录会一并清理摘要。
