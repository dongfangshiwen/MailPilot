# MailPilot 1.0.0：优化前后对比

记录日期：2026-09-10。对比基线为内部构建 32，优化版本为内部构建 33；两版对外版本均为 **1.0.0**，设置页不显示构建号。本文依据已有代码审查、发布说明和测试记录整理，没有为编写本文重新执行接口测试。

**本轮主要减少重复的模型整理请求，并稳定思考区的追加、展开和滚动行为。** 火山单次样例的整理等待明显下降，但并非所有场景都更快；流式渲染和日常模拟器数据恢复仍有未解决事项。

## 1. 优化前为什么慢、为什么感觉思考被覆盖

构建 32 已有上下文预算、滚动摘要、资料分块复用和按账号／会话隔离，并非每次都从零处理。主要瓶颈在于：工具结果占用较大时仍会调用模型整理，而快速整理默认关闭，整理阶段也可能产生较长的模型思考；重复整理完整搜索交换又放大了这部分等待。

界面上的问题来自另一组状态逻辑：单个模型请求结束便自动折叠思考区，后续请求再次展开；重试清空原思考；周期保存与流式更新同时到达时，也存在较旧状态覆盖新内容的风险。这些问题会让用户感觉文字成段跳出、思考反复重来，不能只通过更换模型解决。

此前保留日志中，五次工具整理累计约 309 秒，其中思考约 264 秒。这些记录混合了不同模型或重试，**不能作为截图中一次运行的总耗时**。

## 2. Agent 和上下文处理对比

| 项目 | 优化前：构建 32 | 优化后：构建 33 | 作用及边界 |
|---|---|---|---|
| 快速整理 | 已提供选项，默认关闭；整理可能沿用思考设置 | 升级时一次性启用，以后尊重用户选择；支持的接口在整理任务中关闭思考 | 减少整理等待；正式回答、起草仍跟随输入框开关，不改保存的模型配置 |
| 工具结果进入上下文 | 更容易再次整理完整搜索交换 | 原文保存在当前会话，优先发送来源、必要摘录、读取范围和操作结果 | 模型可通过 `read_evidence` 读取所需原文；摘录不会冒充全文 |
| 工具结果预算 | 存在只计算正文、遗漏标题和协议开销的路径 | 计算最终发送视图，包含标题、链接、来源编号和协议字段 | 避免摘录自身符合预算、完整请求却超限 |
| 压缩触发 | 工具结果接近预算时增加模型整理请求 | 达到 95% 时先复用、去重并缩减已完成工具记录，仍达到阈值才请求模型整理 | 95% 触发阈值和 60% 整理目标不变；不是取消上下文限制 |
| 已完成结果复用 | 设置变化可能让已完成动作或资料缓存失效 | 快速整理设置从内容复用标识分离，兼容旧检查点并重新校验预算 | 开关变化不要求重做已完成搜索或识图；账号、会话和资料约束仍有效 |
| 独立搜索 | 两条查询串行等待 | 同一搜索动作最多并发两条查询，分别保存成功结果，按原顺序合并 | 重试只补缺失项；不保证模型会选择相同查询 |
| 停止后立即重试 | 可能在旧任务保存完成前读取检查点 | 先等待旧任务落盘，再加载最新检查点开始新尝试 | 避免丢失刚完成的结果，不拼接两次正文 |
| 工具轮次上限 | 触及八轮上限时，提示可能作为正常回答返回 | 返回类型化失败，保留草稿和恢复记录 | 避免把未完成任务误报为成功 |
| 诊断 | 阶段归属和最终落盘不够完整 | 按尝试、请求记录耗时、首包、首次思考／正文、计数和结束原因；成功／失败立即保存 | 可以区分搜索、整理与正式生成等待；不保存正文、图片或凭据 |

这里的“先本地精简”主要针对已经保存的工具结果，不等于本地模型压缩，也不等于直接删除用户问题、必要资料或最近对话。

## 3. 思考区和流式交互对比

| 项目 | 优化前：构建 32 | 优化后：构建 33 |
|---|---|---|
| 多次模型请求 | 每次请求结束折叠，下一次再次展开 | 固定一个思考区，按“思考 1、思考 2…”追加请求段 |
| 自动收起 | 工具循环中途也可能触发 | 仅整轮完成且用户没有手动操作时收起 |
| 手动展开／收起 | 容易被下一阶段状态改变 | 用户选择优先，不随工具阶段自动重置 |
| 向上阅读 | 新增内容容易干扰回看 | 离开末尾后保持阅读位置，提供“回到思考末尾” |
| 引用详情返回 | 存在展开状态或阅读位置变化 | 保留思考展开状态及内外两层滚动位置 |
| 失败重试 | 旧思考被清空 | 创建新尝试，旧思考通过“上次尝试”查看；不同尝试不拼接 |
| 历史保留 | 缺少独立的尝试展示 | 最多保留三次旧尝试，每次沿用 128,000 字符保护上限 |
| 流式与数据库状态 | 周期保存可能触发整份历史传输；较旧状态可能迟到 | 活动行保存不再重传全部历史；按订阅及递增顺序过滤重复、较旧快照 |
| 最终展示切换 | 流式展示与最终保存存在交接风险 | 最终结果持久化后再切换到历史展示 |
| 工具处理提示 | 与思考展示容易混淆 | 搜索、图片准备、整理使用独立进度；没有真实思考增量就不模拟思考 |

本轮修复的是追加、状态合并和阅读交互。它不能使模型尚未返回的内容提前出现，也不能据此宣称所有流式卡顿已经消除。

## 4. 真实模型接口：优化前后实测

### 测试条件

- 设备：现有 `MailPilot_API36`，通过完整 `LocalAgent` 路径执行。
- 输入：合成邮件、五张卡片图片、四轮长历史，使用隔离的内存数据库；未上传用户邮件，未发送邮件。
- 模型：设备已保存的 `doubao-seed-evolving` 与 `deepseek-v4-flash` 配置，调用真实模型接口。
- 搜索：固定的合成响应，每次延迟 100ms；**没有测量真实互联网搜索延迟**。
- 样本量：每个型号、每个场景各一次；正式回答保留思考，旧版快速整理关闭，新版开启。
- 重试：在回答请求发出之前注入一次网络异常，再恢复执行；这不是厂商真实断流测试。

### 总耗时和模型请求数

| 型号 | 场景 | 优化前 | 优化后 | 模型请求数：前 → 后 |
|---|---|---:|---:|---:|
| doubao-seed-evolving | 首次分析＋搜索 | 446.3 秒 | 93.8 秒 | 17 → 7 |
| doubao-seed-evolving | 缓存追问 | 21.5 秒 | 41.6 秒 | 1 → 1 |
| doubao-seed-evolving | 失败后重试 | 10.5 秒 | 13.5 秒 | 1 → 1 |
| deepseek-v4-flash | 首次分析＋搜索 | 20.5 秒 | 22.2 秒 | 3 → 3 |
| deepseek-v4-flash | 缓存追问 | 5.9 秒 | 5.9 秒 | 1 → 1 |
| deepseek-v4-flash | 失败后重试 | 3.2 秒 | 2.5 秒 | 1 → 1 |

秒数按原始毫秒记录四舍五入。请求数为模型请求，不能与搜索查询数混用。

### 整理阶段的变化

| 型号 | 优化前整理请求 | 优化后整理请求 | 优化前整理累计耗时 | 优化后整理累计耗时 |
|---|---:|---:|---:|---:|
| doubao-seed-evolving | 8 | 2 | 353.2 秒 | 8.6 秒 |
| deepseek-v4-flash | 0 | 0 | 0 秒 | 0 秒 |

该表按每个型号的测试记录汇总 `compression` 阶段，时间来自请求的 `elapsedMs`。原始证据：[构建 32](test-evidence/build33/live-baseline32.json)、[构建 33](test-evidence/build33/live-current33.json)。

### 如何解读

1. 火山样例中，重复模型整理确实是重要瓶颈，本轮减少了这部分请求和等待。
2. 旧版火山首次分析最终触及八轮工具上限，只返回 43 字上限提示；新版返回 222 字回答。实际搜索查询数也从 15 变为 4。两次输出、工具选择和完成状态不同，**不能将 446.3 秒与 93.8 秒换算成稳定的同任务提速倍数**。
3. DeepSeek 本例原本没有整理请求，整体耗时没有明显改善；火山缓存追问和重试还出现更长等待。请求数未增加，仍需多次重复测量正式模型生成延迟。
4. 追问和重试均没有再次上传图片。两组首次分析仍包含一次视觉助手读取，符合此次保存的主模型配置；这组测试不是视觉主模型直接图文回答的单请求验证。
5. MailPilot 使用用户配置的 API，无法证明与 DeepSeek APK 使用相同后端、调度和额度。因此不能用该对照宣称达到或复制 DeepSeek APK 的速度。

## 6. 代码审查与清理结果

本轮清理和修复集中在实际重复工作与状态冲突，详见 [代码审查记录](CODE_REVIEW_BUILD_33.md)。

- 合并工具结果预算口径，补齐标题、链接与协议开销。
- 用已完成结果的精简视图和覆盖位置，减少重复整理整份搜索交换。
- 将快速整理选项与已完成内容的缓存身份分开，保留必要旧检查点兼容。
- 移除工具轮次结束自动折叠的旧行为，统一为整轮完成策略。
- 去除周期保存当前回答引起的整份历史传输，过滤重复和较旧增量状态。
- 修复停止／重试写入竞争及最终状态未及时保存的问题。
- 将工具轮次耗尽改为明确失败，避免误报任务成功。

仍被调用的旧接口兼容回调没有以“冗余”为由直接删除。本轮审查也不是对所有第三方依赖的完整安全审计。

## 7. 未改变的产品和安全边界

- 每个账号、会话独立管理上下文和资料缓存，不将其他会话历史直接混入当前请求。
- 上下文压缩触发阈值保持 95%，整理目标保持 60%；正式模型的已保存配置与自定义额度继续保留。
- 模型没有 SMTP 发送工具。草稿确认、版本校验及发送状态保护继续执行，整理和重试不会新增发送授权。
- 未完成正文不作为成功草稿或有效图片观察；取消、失败和重启保留已有有效检查点。
- Room 保持 v9，新状态沿用版本化轮次记录，兼容旧思考文本。
- APK 沿用原签名，版本保持 1.0.0；设置页保留发送确认提示，不显示内部构建号。

## 8. 测试事故、恢复状态与后续工作

### 日常模拟器数据丢失：尚未恢复

本轮首次 Profile 测试错误地对日常 API36 的 `app.mailpilot` 使用了 `flutter drive` 默认结束流程，测试结束卸载应用，清除了原有 **1 个邮箱账号、2 个模型配置、4 个会话、42 条聊天、2 个草稿、7 条视觉缓存**。这是测试操作错误，不是 Room 迁移失败。

目前尚未恢复测试前完整数据。`.tools/recovery33` 保存的是事故后的磁盘副本，不是已经验证的事故前备份；它不进入源码包，也不随普通缓存清理。不能用临时设备合成数据覆盖升级成功来替代日常设备的数据保留结论。

测试脚本现使用 `app.mailpilot.validation` 隔离包名，安装前校验 APK 包名，并加入 `--keep-app-running`；发布覆盖安装使用 `adb install -r`。修复后的脚本已实跑，但这些保护不会自动恢复之前丢失的数据。

### 清理状态

Flutter 构建缓存已清理，临时发布验证设备与隔离测试进程已停止。目录删除／测试包卸载的合并命令曾被自动审批拒绝，仅返回 `blocked by policy`；相关目录和隔离测试包仍保留，没有重新绕过该拒绝。恢复副本单独保留。

### 仍需验证或改善

| 后续事项 | 当前依据 | 下一步建议（尚未完成） |
|---|---|---|
| 正式回答延迟 | 火山缓存追问本次仍需 41.6 秒 | 固定输入、配置和输出要求，多次测量首包、首次正文、生成时间及分位数 |
| 真实搜索表现 | 当前对照使用固定合成搜索服务 | 单独测量真实搜索耗时，区分搜索服务、工具规划与模型生成 |
| 流式帧稳定性 | 软件渲染样本的栅格化 P95 超过一帧预算 | 在真机及同条件旧版上复测，定位排版、绘制与滚动开销 |
| 厂商断流恢复 | 本轮重试样例为请求前故障注入 | 增加真实服务异常观测，不能承诺彻底杜绝外部服务断流 |
| 日常模拟器数据 | 事故前完整记录尚未恢复 | 基于可用备份继续恢复检查，保留事故后副本 |
